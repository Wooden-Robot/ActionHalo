# Android 0.11.9 菜单圆环生命周期与诊断

## 证据与边界

用户在 0.11.8 提供的报告表明服务已连接、系统已启用、省电已豁免、相关开关已打开；`DIRECT_HALO_SHOWN` 只能说明曾成功添加窗口，缺少时间、来源和随后隐藏／删除的原因。`FILTERED` 同时包含不可见、密码、敏感节点等情况，不能据此认定原子笔记的具体阻断原因。用户随后明确：微信圆环一闪而过，原子笔记完全不出现。

后续 0.11.9 真机报告通过新增阶段确认了 `MENU_MATCHED → HALO_NO_SPACE → HALO_ATTACHED`，用户反馈微信完全不显示。该首帧不可见原因及修复见 [0.11.10 手柄穿透记录](handle-region-0.11.10.md)。

本次仍未连接用户手机。使用 API 35 无账号模拟器、固定文本和独立测试 APK 的真实自定义菜单构建最小反馈循环，不能代替 vivo / SDK 36 / 真实微信及原子笔记验证。

## 可复现的问题与修改

`FocusedClipboardOverlayTest#selectionEventWithoutRangeKeepsTheExistingCustomMenuHaloVisible` 在真实菜单和圆环出现后，通过来源 TextView 发出范围不可用（事件和节点均无有效范围）的选区事件。旧代码把所有无有效范围的选区事件视为取消，即使复制菜单仍然存在，也会删除并重建圆环。修复前连续两次失败于“同一圆环实例应保持可见”的断言，各约 4 秒；日志为 `/private/tmp/actionhalo-flash-red.log` 和 `/private/tmp/actionhalo-flash-red-repeat.log`。

共享菜单观察器现在仅在明确的相等非负端点表示选区收拢时走该取消分支；缺少范围信息本身不删除仍由真实复制菜单支持的圆环。后续菜单、来源、授权、复制新鲜度及文本长度检查保持有效。重新定位、选文手柄保护及初选静默规则没有撤回。

这验证了一条可能造成闪烁的路径，并不证明真实微信只发生了这种事件。

## 下一次真机诊断

报告增加以下当前进程内的固定元数据，不收集选文、菜单标签、剪贴板或应用标识：

- 最近菜单检查的结果与相对时间：无前台、不可读、没有子窗口、来源不符、没有有效复制控件、歧义或成功匹配。
- 最近菜单扫描中排除的控件类别：隐藏、密码、可编辑、敏感、未支持的控件或遍历被截断。该集合描述扫描中遇到的排除项，不保证其中某项就是整个菜单失败的唯一原因。
- 最多 24 条固定阶段与相对时间：长按、缺失范围、明确取消、创建／移除窗口、外部触摸、等待菜单恢复、没有摆放空间、恢复可见，以及普通选文路径的具体过滤原因。

「检查自动弹出」同时重置普通选文和菜单诊断。关闭示例圆环后，每次只在一个应用复现，再立即返回复制报告。原子笔记问题尚待这份单次报告定位，不以放开敏感内容或扫描聊天正文来猜测解决。

## 验证

- 定向 14 项通过，涵盖上述失败用例、未支持控件的准确拒绝报告、真实选区取消和全部外观／手柄边界测试：`/private/tmp/actionhalo-flash-targeted.log`。
- 61 项 JVM 测试通过；Lint 0 错误、6 项警告：`/private/tmp/actionhalo-flash-final-build.log`。
- 首次完整相关设备回归 82 项：79 通过、2 条件跳过、1 失败。失败为 `explicitButtonModeSupportsLegacyWebViewWithoutSelectionTextOrRanges`，未等到按钮模式入口；不能把此轮写为全部通过。日志：`/private/tmp/actionhalo-flash-regression.log`。
- 失败项单独复测通过，随后与其前五项组合复测六项均通过：`/private/tmp/actionhalo-flash-webview-recheck.log`、`/private/tmp/actionhalo-flash-webview-sequence.log`。生产代码和断言条件未因这次超时而改变；仅为超时断言补充固定原因报告，原因仍未确定。
- 两项跳过依赖另装的 Telegram 合成宿主和 Via 浏览器测试条件。这里的合成菜单成功仍不能作为真实微信或原子笔记已修复的结论。
